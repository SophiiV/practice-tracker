# Лабораторна 12: рефакторинг із патернами

У «Трекері Практики» впроваджено два патерни: **Strategy** для розрахунку оцінки та **Factory Method** для підготовки договору й щоденника. Вони працюють у наявних сервісах застосунку. Маршрути HTTP, таблиці SQLite, шаблони DOCX і правила доступу збережено.

## Структура матеріалів

1. `before/gradeService.js` і `before/documentService.js` — точні копії початкових сервісів.
2. `diagrams/before.mmd` і `diagrams/after.mmd` — UML класів до та після; їх можна відкрити в редакторі з підтримкою Mermaid.
3. `../backend/src/patterns/grades/` — стратегії та контекст.
4. `../backend/src/patterns/documents/` — продукти та творці документів.
5. `evidence/` — фактичні журнали перевірок, а не очікувані результати.

## Strategy: змінна формула, спільний виклик

До змін `gradeService.calculate()` одночасно містив формулу середнього й переведення в ECTS. Для іншої формули довелося б редагувати цей метод.

Після змін `GradeCalculator` є контекстом. Він приймає об’єкт стратегії і викликає його `calculateFinalScore(enterpriseGrade, teacherGrade)`. Шкала ECTS залишається спільною у контексті. `AverageGradeStrategy` реалізує початкове округлене середнє, `WeightedGradeStrategy` — зважене середнє. Базовий `GradeStrategy` описує однаковий контракт методів; це навчальний аналог interface у JavaScript.

```js
const average = new GradeCalculator(new AverageGradeStrategy());
const weighted = new GradeCalculator(new WeightedGradeStrategy(0.4, 0.6));
average.calculate(80, 95);  // finalScore: 88
weighted.calculate(80, 95); // finalScore: 89
```

Ваги 40/60 є прикладом іншого алгоритму, а не затвердженим правилом оцінювання. `gradeService.calculate(a, b, strategy)` дозволяє серверному коду передати стратегію. `gradeService.save()` викликає його без третього аргументу, тому офіційне збереження використовує початкове середнє. Поля `strategy`, ваги або `finalScore` із клієнтського HTTP-запиту не змінюють формулу. Розрахунок із Weighted не змінює наступні розрахунки чи записані оцінки.

Щоб додати новий алгоритм, створи клас із методом `calculateFinalScore(a, b)` та передай його контексту. Код `GradeCalculator` змінювати не потрібно. Валідація оцінок у межах 0–100 виконується наявним сервісом перед збереженням.

## Factory Method: різні документи, спільна підготовка

До змін `documentService.get()` містив великий умовний вираз для полів договору або щоденника. Логіка вибору виду документа змішувалася з доступом до БД, перевіркою прав і запуском Python.

Після змін `PracticeDocument` описує продукт: `defaults()`, `validate()`, `generationInput()`. Його підкласи `ContractDocument` і `DiaryDocument` задають власні початкові поля. Вони використовують наявний валідатор, щоб не дублювати перевірки дат і реквізитів.

`DocumentCreator` містить спільні сценарії `getData()`, `validate()` і `prepareGeneration()`. Усередині них він викликає **фабричний метод `createDocument()`**. `ContractDocumentCreator` повертає `new ContractDocument()`, а `DiaryDocumentCreator` — `new DiaryDocument()`.

Це саме Factory Method: підкласи Creator перевизначають метод створення Product, а успадкований сценарій користується створеним продуктом. `Map` у `getDocumentCreator(kind)` лише обирає потрібного творця; сама таблиця відповідностей не є фабричним методом.

Ланцюжок експорту: HTTP → `documentService.generate()` → Creator → `createDocument()` → Product → перевірений JSON → наявний `fill_document.py` → DOCX. Сервіс і далі перевіряє права, читає та зберігає дані; Python і далі заповнює оригінальний шаблон.

При додаванні третього типу потрібно створити Product та Creator, зареєструвати Creator, а також забезпечити поля, валідацію, сховище і шаблон нового виду документа. Патерн прибирає умовне створення продуктів зі спільного сценарію, але не створює ці частини автоматично.

## Запуск перевірок

Потрібні Node.js 22.13+ із `node:sqlite`, npm і Python 3. Якщо залежності ще не встановлені, виконай `npm ci` у `backend`. Команди нижче запускаються з папки `backend`:

```sh
npm run demo:patterns
npm run test:patterns
npm test
```

Перша команда показує 88 і 89 для тих самих вхідних оцінок, назви творців та їхніх продуктів. Вона не імпортує БД. Друга запускає 24 перевірки патернів. Третя запускає всі 94 перевірки поточної версії; під час первинного рефакторингу їх було 93. Тести самі створюють окремі БД у тимчасових папках і видаляють їх після завершення. Для HTTP-перевірок потрібна можливість відкрити локальний порт.

Якщо Python має іншу назву або шлях, передай змінну `PYTHON_BIN`, наприклад `PYTHON_BIN=/шлях/до/python3 npm test`. Експорт використовує лише стандартну бібліотеку Python.

З кореня репозиторію додаткове точне порівняння з копією формули до змін запускається командою `node refactoring/verify-grade-equivalence.mjs`.

## Результат і обмеження

Strategy відокремлює алгоритм оцінювання, а Factory Method — створення типу документа. Незмінність початкової поведінки перевірено регресійними тестами, порівнянням усіх цілих пар оцінок і перевірками експорту документів.

Ціна рефакторингу — чотири додаткові файли патернів і більше переходів між класами. Для двох незмінних формул або документів це було б зайвим у дуже малому проєкті; тут поділ доречний як навчальна демонстрація точок розширення, які вже існують у застосунку. Патерни не гарантують правильності самі собою: права доступу, транзакції, валідація і тести залишаються необхідними.
